Review summary: The diff correctly narrows the credential guard so remote GitHub API calls and http(s) URLs do not trigger the local-credential default-deny. The tests cover both directions well. I found one real security-scope question and one minor coverage gap.

- **ask-user:** The fix strips the endpoint argument from any `gh api repos/.../contents/...` call before the sensitivity check, with no check for repo visibility. The code comments and PR title assert the target is a "PUBLIC repo," but nothing in `_strip_gh_api_endpoint` or `_GH_API_ENDPOINT` confirms this. An authenticated `gh` session can also call this same endpoint shape against a **private** repo the user can access, and the guard will now let a segment like `gh api repos/<owner>/<private-repo>/contents/.env` through with no local-path check. Confirm whether the guard's threat model excludes "remote reads of a private repo via an authorized token" on purpose, or whether this needs a visibility check. No test exercises a private-repo endpoint, so this gap is not proven safe or unsafe by the test suite either.

- **ask-user:** `_GH_API_ENDPOINT` lists only `repos|orgs|users|user|gists|search|graphql|rate_limit|meta` as recognized remote route prefixes. Real GitHub REST top-level routes also include `notifications`, `issues`, `licenses`, `apps`, `markdown`, `emojis`, and others. Calls to those routes will still fall through to the old default-deny, unlike the `repos/...` cases fixed here. This is a safe direction (no new false-negative), but confirm it is a deliberate narrow scope and not an oversight, since the PR title states the broader claim "a remote resource is not a local credential store."
