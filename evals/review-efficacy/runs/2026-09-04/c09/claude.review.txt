Reviewed the diff. Found one real bug against the script's own stated design, plus a design mismatch in another detector, and no tests for the new module.

- **auto-fix:** `is_compound_inspection` (line 155) checks `if len(segments) < 2: return False`, so a 2-segment chain is counted as compound-inspection. This contradicts the function's own docstring ("True for a chain of three or more read-only segments") and the comment directly above it ("Three, not two: a two-segment chain is cheap and common, and counting it would drown the signal the rule is actually about."). The threshold should be `< 3`, not `< 2`.

- **ask-user:** `_READ_ONLY_SUBCOMMANDS` includes bare `"pr"`, `"issue"`, `"repo"`, and `"api"` (line 81). `_segment_is_read_only` (lines 129-135) only inspects the first subcommand token for `git`/`gh`, so `gh pr merge`, `gh pr close`, `gh pr edit`, `gh repo delete`, and mutating `gh api` calls all match `sub in _READ_ONLY_SUBCOMMANDS` and get treated as read-only. This is the exact failure mode the comment at lines 76-77 warns against ("A chain ending in a push or a merge is a real ordering dependency, so it must not be counted as inspection.") Needs a decision on how to enumerate the actual safe actions under `pr`/`issue`/`repo`/`api` rather than matching the namespace alone.

- **auto-fix:** In `_segment_is_read_only` (line 133), `if sub in ("-c", "-c"):` is a duplicate-value tuple — both entries are identical, so this branch is dead code (and would still be dead even with the presumably intended `("-c", "-C")`, since `_subcommand` already filters out any token starting with `-`, so `sub` can never equal `-c`). It doesn't currently affect output (the `-C`/`-c` case is handled correctly by `_subcommand_after_path` below), but it's leftover/incorrect logic that should be removed or fixed to reflect actual intent.

- **ask-user:** The PR adds ~370 lines of new detector logic (four regex/parsing detectors with several edge cases: quoted paths, `-C`/`-c` flag positions, env-var-prefixed tokens) with no accompanying test file in the diff. Given the module's own stated purpose is to make rule adherence measurable/verifiable, shipping the detectors themselves untested is worth flagging.
