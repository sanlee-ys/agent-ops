- **ask-user:** `_HEREDOC` (line 164) removes everything from `<<` to the terminator, including the rest of the marker line and any body that a shell executes. `cat <<EOF && git reset --hard` and `bash <<EOF` with a destructive body both classify as clean and pass. The fix needs a decision: strip only bodies of non-executing commands, or keep the body when the lead command is a shell.
- **ask-user:** `if OVERRIDE in command` (line 402) is a substring test, but the docstring and PR say "prefix". `git reset --hard # RISK-OK` or a `RISK-OK` inside a commit message disables the guard. It also disables the block bucket (`rm -rf /`), which defeats the exit-2 backstop that the PR claims. Decide whether to require the token at the start of the command, and whether `block` should be overridable at all.
- **ask-user:** The `warn` bucket prints an explicit `permissionDecision: "allow"` (lines 353-358). The `allow` bucket prints nothing. An explicit hook allow may auto-approve `rm -rf <dir>` or `git branch -d -f`, which the existing `ask` rules would otherwise prompt for. Warn should probably emit context only. This depends on harness semantics, and the PR admits they are unmeasured.
- **ask-user:** `_dangerous_target` treats every absolute path except `/`, `~`, a drive root and `.git` as project-relative. `rm -rf /etc`, `/usr`, `C:\Windows` and `"$HOME/"` (trailing slash) score `rm.recursive` (0,1), which is only `warn`. This contradicts the comment that dangerous paths keep the block.
- **ask-user:** `classify` only looks at the lead token. `sudo rm -rf /`, `bash -c "git reset --hard"`, `env X=1 git clean -fd` and `xargs rm -rf` are never classified. `_SPLIT` also cuts inside quotes, so `git commit -m "x; git reset --hard"` produces a false confirm. State whether these are accepted limits, and add them to the tests if they are.
- **ask-user:** In `_classify_git` (lines 270-272), `a in {"--no-verify","-n"} and a == "--no-verify"` reduces to `a == "--no-verify"`, so `-n` is dead. `git commit -n` (short for `--no-verify`) is missed. `-n` means something else for `push` and `merge`, so the fix is per subcommand, and the intended behavior is a guess.
- **ask-user:** `_emit` ignores `payload`, so warn and confirm always print Claude-format `hookSpecificOutput` JSON. A Cursor payload is detected in `_allow` (`{"permission": "allow"}`). Confirm and warn produce no verdict Cursor understands and effectively allow there. Block still works through exit 2.
