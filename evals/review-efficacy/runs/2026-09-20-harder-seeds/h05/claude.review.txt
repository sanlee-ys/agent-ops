v1.1 does what the PR describes, with one usability risk and one robustness gap. The test file, `hooks/README.md` and the derived plugin copy are not in the diff I received, so I could not check the "22 → 36 cases" and "byte-identical" claims.

- ask-user: `FORBIDDEN_ENV_KEYS` blocks `ANTHROPIC_API_KEY`, `ANTHROPIC_BASE_URL` and `ANTHROPIC_AUTH_TOKEN` in `env`, and the check reads the file's current state. A user who legitimately sets one of these in `settings.json` (a proxy, a gateway, a key) would have every later edit blocked, including the edit that removes the key. That contradicts the PR's rule that checks fire only on "unambiguously dangerous" values and never on "merely unusual" ones. Question: should these keys be blocked outright, or only when the value changes or points at a non-default host?

- auto-fix: `_guard_is_wired` iterates `entry.get("hooks") or []` without checking the type. If `hooks` is a truthy non-list such as `5` or `true`, this raises `TypeError`, and the code shown does not catch it. The PR pins "junk in the `hooks` tree" as allowed and the module says it fails open loudly. Guard the value with `isinstance(..., list)` so junk is skipped and the guard is reported as not wired, as the other non-list cases are.

- auto-fix: `needle in command` matches `credential-guard.py` as a substring of `not-credential-guard.py`, `credential-guard.py.bak` or `echo credential-guard.py`. This is the same substring weakness v1.1 removes at the guard-name level. Match the `<guard>.py` filename as a whole path token, for example after a path separator or whitespace and before whitespace or the end of the string. This is mechanical and does not change intent.

- Scope fidelity: the diff adds nothing unrequested and drops nothing v1.0 refused. The permissions, `env` and structural checks all match the PR description. The hook file changes are the only part of the diff I could review.
